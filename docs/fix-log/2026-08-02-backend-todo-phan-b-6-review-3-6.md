# Fix log entry — 2026-08-02 02:01

## Prompt

Backend TODO Phần B #6 (review 3.6): `POST /api/auth/login` in [server/routes/auth.js](server/routes/auth.js) returned 401 immediately when `db.getUserByUsername()` found nothing, so an unknown username skipped bcrypt entirely while a known username paid for a full `bcrypt.compare`. Response time alone therefore revealed whether an account existed — a username-enumeration oracle in front of the login form. The original review could not quantify it (bcrypt would not load on the review machine, see TODO Phần A #4); this run measured it.

## Action

`DUMMY_PASSWORD_HASH`, a hardcoded cost-12 bcrypt hash, added next to the route's other constants. The lookup no longer early-returns: `bcrypt.compare(password, user ? user.password_hash : DUMMY_PASSWORD_HASH)` always runs, and the rejection became `if (!user || !match)`, so both failure modes do the same work and return the identical status and message.

## Decision

Hardcoded per `instruction.md` §B6's explicit "cố định" requirement — a hash generated at startup (hashing a random or empty string) would make the dummy comparison's cost depend on how it was produced, which is the very variance the defence removes. Cost factor 12 matches `config.BCRYPT_ROUNDS`: a cheaper dummy would finish faster than a real compare and hand the signal straight back, so a test asserts the two stay in sync. Nothing else in the login path changed — the 400 for a missing username/password still short-circuits before any hashing, which is correct (it leaks nothing about accounts).
