Backend TODO Phần B #7 (review 3.2): `RoomManager.createRoom()` enforced only a global `MAX_ROOMS` cap and a one-room-per-user rule, so a single client could mint guest accounts and take the entire 10-room pool, locking everyone else out of creating a room. `instruction.md` §B7 offers two alternatives and says to pick one: (a) a per-IP/account quota, or (b) forbid guests from creating rooms at all. [LobbyHandler.js:42-56](server/socket/handlers/LobbyHandler.js#L42-L56) passes `socket.handshake.address` through. Deliberately not 1, per `TODO.md`: phones behind a carrier NAT and everyone on one office/home wifi share a public IP, so 1 would refuse real users who did nothing wrong — 3 still stops one client from taking the whole pool.

## Decision

`TODO.md` flagged the real risk as "must remember to decrement on BOTH the idle-timeout path and the explicit-close path, not just one". Sidestepped that class of bug entirely rather than trying to get every decrement right: the quota is **derived by scanning `this.rooms`** at create time instead of kept in a tally. A tally has to be decremented on every teardown path — explicit close, last user leaving, idle cleanup, and any path added later — and permanently leaks quota the first time one is missed; a derived count cannot drift, because a destroyed room is gone from the map by definition. With `MAX_ROOMS` = 10 the scan is trivially cheap. A connection with no known address is left unlimited on purpose (never refuse a real user because the address was unavailable). Known limitation, **not** this item's call: behind a reverse proxy every connection reports the proxy's address, collapsing all users into one quota — that needs `app.set('trust proxy', <hops>)`, tracked as TODO Phần A #1, and is noted in a comment at the call site.
