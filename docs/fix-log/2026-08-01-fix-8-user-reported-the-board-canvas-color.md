# Fix log entry — 2026-08-01 22:30

## Prompt

Fix #8: user reported the board canvas color palette is too light and uncomfortable to look at for extended play. Investigation of the board renderer, `BoardRenderer` in [client/js/board.js](client/js/board.js), found every canvas color (background gradient, grid lines, star points, coordinate labels, highlights, piece ink) was a hardcoded hex/rgba literal that never read the app's `--c-*` theme variables in [client/css/main.css](client/css/main.css) — so the board stayed glaringly light even when a user switched the rest of the app to dark theme via `setTheme()` in [client/js/settings-panel.js](client/js/settings-panel.js).

## Action

Added four `--board-*` custom properties (`--board-bg`, `--board-accent-rgb`, `--board-ink-rgb`, `--board-pending-rgb`) to both `[data-theme="light"]` and `[data-theme="dark"]` blocks in main.css. Added `_readBoardTheme()` to `BoardRenderer` (board.js), cached once per frame as `this._theme` at the top of `_draw()` (line ~349), and a `MutationObserver` on `document.documentElement`'s `data-theme` attribute in the constructor so an open board repaints live on theme toggle (settings-panel.js dispatches no change event to hook into). Replaced the hardcoded literals with `this._theme.*`-derived values in the non-stone (`paper`/`caro`) branches of `_drawBackground()`, `_drawStarPoints()`, `_drawCoordinates()`, `_drawLastMoveHighlight()`, `_drawHoverHighlight()`, `_drawPendingHighlight()`, and `_drawBlackPiece()`.

## Decision

Decided to make the board theme-aware rather than just picking a single softer standalone palette, because the app already ships a fully-built dark theme that the board simply never joined — reusing it fixes the glare for exactly the condition most likely to cause eye strain (dark room, board still blazing white) without inventing a third, undocumented color scheme. Researched WCAG 2.1 contrast guidance before choosing values: 4.5:1 for text-like elements (coordinate labels), 3:1 for large/graphical UI elements (grid lines, highlight rings). This also surfaced a pre-existing bug while auditing: the original coordinate-label alpha (0.5 over a teal-700 base) only reached ~2.1:1 against the light background — below even the graphical minimum — so the light theme's accent was darkened to teal-800 (`15, 94, 89`) and label alpha raised to 0.85, lifting it to ~5.05:1 (star points, being decorative, were left at alpha 0.6 / ~2.9:1). **Deliberate scope limit, stated explicitly per the task's decision fork:** only the default `paper`/`caro` outline display mode was made theme-aware. The optional `stone` display mode's radial-gradient background and filled black/white discs were left untouched on purpose — measured contrast of the near-black stone gradient (`#020202`) against a plausible dark board bed came out to ~1.7–2.1:1, i.e. inverting that background would make black stones nearly invisible. Traditional Go boards solve this with a fixed mid-tone board regardless of room lighting, so `stone` mode keeps its existing light backdrop in both themes; this is called out in a code comment next to `--board-bg` in main.css so a future maintainer doesn't "fix" it into the same trap. The white-piece ink (rose-600 outline) and win/pending overlay hues were left unthemed since they already read acceptably (≥3:1) against both new background tones.
