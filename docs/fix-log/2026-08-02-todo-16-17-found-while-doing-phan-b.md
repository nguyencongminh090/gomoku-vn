## Decision

Normalizing `winner` itself, not just adding `winner_name`, is the part that actually closes #16 for legacy data: on a pre-normalization row, `winner` **is** the raw secret id — returning it unchanged in the `winner` field would leak exactly what stripping `black_player_id`/`white_player_id` was supposed to prevent, just under a different key. Caught by a test that mirrors the shape of real legacy data (see Evidence) rather than reasoned about in the abstract. Kept the fallback-chain's existing behavior of resolving guest-vs-guest legacy rows to `null` (generic "Có người thắng" / "Người chơi" on screen) rather than the old client code's last-resort guess of treating a short `winner` string as a literal name — that guess could show a raw guest id like `guest_ab12cd34` as if it were a name, which is worse than the honest generic fallback. `getPlayerHistory()` and `server/scripts/admin.js`'s own direct queries were deliberately left untouched: neither is reachable from an unauthenticated client (the admin script runs local SQL directly, not through this module), so they were never in scope for the leak this closes.
