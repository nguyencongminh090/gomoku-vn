# Fix log entry — 2026-08-03 01:52

## Prompt

TODO.md Phần B #32 (from the 2026-08-03 whole-codebase security review): `isValidDisplayName` in [server/routes/auth.js](server/routes/auth.js) only checked length (2-24 chars) and placed no restriction on which characters a display name may contain. Not an open vulnerability — the audit confirmed every client render path (`room-ui.js`, `lobby.js`, `history.js`) escapes correctly before touching `innerHTML` — but there was no barrier at the source, so a future render site that forgot to escape would turn a stored display name into a live XSS vector.

## Action

Added a `DISPLAY_NAME_FORBIDDEN` deny-list regex to [server/routes/auth.js](server/routes/auth.js) rejecting the five HTML/attribute/JS-string-significant characters `< > & " '` plus C0/C1 control characters (`U+0000-U+001F`, `U+007F-U+009F`, which covers newline/CR/tab/NUL and invisible formatting). `isValidDisplayName` now applies it to the trimmed value after the existing length check; the 400 response message was updated so a rejected user sees *which* rule they broke rather than a length message about a name that is already the right length. Single call site (`POST /api/auth/register`) — there is no rename route in this codebase, and guest names are server-generated from `config.GUEST_NAME_ADJECTIVES/NOUNS`, so nothing else needed touching. No client files changed, so no `?v=N` bump applies.

## Decision

Followed `instruction.md` §B32's central constraint exactly: **deny-list, not an ASCII allow-list**. `[a-zA-Z0-9 ]+` would reject most of this app's actual users ("Nguyễn Văn A") — that regression is the specific risk §B32 names, so the accept-side test cases (Vietnamese diacritics, non-Latin scripts, Latin-1 accents) are treated as load-bearing rather than incidental. Kept the forbidden set to exactly the characters §B32 listed — deliberately did **not** also ban backtick or backslash, which would be defensible on the same reasoning but were not part of the given scope (`CLAUDE.md` scope discipline). Left the existing client-side escaping untouched: this is a second layer at the source, not a replacement for the layer at the destination. **Known narrowing, accepted:** the apostrophe ban also rejects genuine names like "O'Brien" / "D'Angelo" — no such regression risk for the Vietnamese user base this app targets, and `'` is exactly the character that breaks out of the `onclick="joinRoom('…')"` JS-in-attribute contexts this codebase uses, but it is a real (if narrow) tradeoff rather than a free win.
