## Decision

The user specified `#D9D9D9` as a single background, not a light/dark pair, but literally reusing that light gray as `--board-bg` in the dark theme block too would have undone Fix #8's original glare fix — the whole point of making the board theme-aware was so it goes dark with the rest of the UI. Read `#D9D9D9` as the **light-theme** value and derived an analogous dark-theme set in the same neutral-gray-plus-blue-plus-red identity rather than leaving Fix #9's warm walnut in place, since mixing a gray/blue "Paper Style" light mode with a wood-toned dark mode would read as two different apps depending on theme. Dark theme: `--board-bg: #262626`, `--board-accent-rgb: 150, 168, 214`, `--board-ink-rgb: 147, 197, 253` (blue-300, bright enough against the dark bed). The circle's bright red was kept identical in both themes rather than split into a light/dark pair, because red already meets the graphical contrast minimum against both backgrounds (see Summary) and a hue that shifts with theme would make it harder for a player to recognize "their" piece color at a glance. **Wall colors, calculated via the WCAG contrast formula as asked:** solved for the gray value whose relative luminance yields a 4.5:1 ratio against each background using `contrast = (L1+0.05)/(L2+0.05)`; light theme resolves to `rgb(97,97,97)` (`--board-wall-dark-rgb`), dark theme to `rgb(140,140,140)` — each theme's brick "dark" tile is that anchor exactly, with mortar/base/light steps offset ±20-40 luminance units around it for texture rather than independently solved (only the anchor tile's contrast was a hard requirement; the others exist for depth, bounded by borders/gaps that carry legibility regardless of their own contrast).
