**Row 35 findings (ad-hoc run against real caps temporarily raised, then reverted):**
- Ramped concurrent 2-player games (raw `socket.io-client`, JWTs signed directly to bypass the guest-auth rate limiter — see design note below) from 200 to 2000 simultaneous players, each pair actually playing paced real moves.
- **200–1200 concurrent players:** clean. `game:move` round-trip latency p50 ≈ 1-2ms, p99 ≈ 25-66ms. Server RSS grew from a ~90MB baseline to ~180MB. Server CPU stayed at **~11% of one core** — nowhere near saturated.
- **2000 concurrent players:** a growing tail of pairs (up to ~15% in the fastest/least-padded run, ~2% once given a generous 60s grace) timed out waiting for the game to start. Root-caused this as **not** CPU or memory exhaustion (both stayed low) — most likely event-loop/processing backlog from firing an entire batch as one instantaneous zero-paced burst (no real user base clicks "ready" in the same millisecond), possibly compounded by the load-generator itself being a single Node process also contending for its own event loop at that scale. Longer timeouts recovered most of the "failures," meaning they were mostly *slow*, not *lost*.
- **Bottom line:** the app comfortably handles at least ~1200 simultaneous real players (600 concurrent games) on this machine (8 cores, 14GB RAM) with no meaningful degradation and low resource use. Genuine ceiling likely sits meaningfully higher, but pinning down a precise "up to N, fails at N+1" number needs a better-paced, multi-process load generator (this single-process harness becomes a confound above ~2000) — not yet resolved as a hard number, and not built as a permanent regression test this session per explicit instruction to stop performing tests once the matrix work was done.
- The production ceiling remains the config-defined 200 room-members (`MAX_ROOMS=10 × MAX_USERS_PER_ROOM=20`) regardless of what raw concurrency the process can absorb — this run answers "how much headroom exists under the current caps," not "what happens with the real caps at scale," since the caps themselves were raised to get a real number at all.

**Row 35 design note (read before implementing):**
- **Don't drive this with Playwright browser contexts.** Each real Chromium context is itself heavy (its own process, real RAM/CPU) — at any serious concurrency you'd exhaust the *test machine's* resources long before the *server's*, and you'd be measuring Playwright's overhead, not the server's. Use a plain Node script with many raw `socket.io-client` connections instead (same technique already used for the "outsider" probes in `e2e/security-boundary.spec.ts` / `e2e/kick-blocked-interrupted.spec.ts`, just at scale) — optionally still exercised as one Playwright `test()` that shells out to / imports that script, so it stays discoverable in the same suite.
- **The structural ceiling is config-defined, not open-ended**, per `server/config.js`: `MAX_ROOMS=10`, `MAX_ROOMS_PER_IP=3`, `MAX_USERS_PER_ROOM=20` (2 players + 18 spectators) → a hard ceiling of **200 concurrent room members server-wide**. "As much as possible" means driving at/past exactly these caps and asserting the server rejects gracefully past them (no crash, no leak) — not an unbounded ramp.
- **`POST /api/auth/guest` is rate-limited to 20 req/15min per IP** (`server/routes/auth.js`) — reaching even one room's 20 users, let alone 200 server-wide, is impossible through the real endpoint from one test-harness IP. Bypass it the same way a load-test harness legitimately would: sign JWTs directly with `jsonwebtoken` using the same shape `signToken()` builds in `server/routes/auth.js` (`{ userId, username, displayName, isGuest: true }`, `config.JWT_SECRET`, `config.JWT_GUEST_EXPIRY`) — this is a test-only shortcut against the local server, not something exposed to real users, so it's legitimate here but must never be framed as "testing the real guest-auth path" (that's rows 20/22's job).
- **`MAX_ROOMS_PER_IP=3` also blocks room *creation* at scale from one IP.** Since each minted JWT is a distinct `userId` but they'll all originate from the test harness's one source IP, only 3 of them can ever successfully `room:create`. Fill the rest of the 10-room server cap by having the first few creator identities create rooms, then join everyone else in as spectators/players across those rooms (respecting `MAX_USERS_PER_ROOM=20` each) — don't treat hitting `MAX_ROOMS_PER_IP` as the test's failure mode, that's expected and is what row 2 already covers separately.
- **`MAX_EVENTS_PER_SECOND=50` / `FLOOD_DISCONNECT_STREAK=5`** (`SocketHandler.js` io.use middleware, also row 23 — now Passing, `e2e/flood-protection.spec.ts`) will force-disconnect any single socket that floods — so "data flow" measurement (move round-trip latency under load) must pace each simulated client well under that per-socket ceiling, or you're just re-testing row 23's flood guard by accident.
- **Metrics to capture**, at minimum: server process RSS/heap (`process.memoryUsage()` — needs a way to read it out of the running dev server, e.g. a debug-only endpoint or attaching `--inspect`/a monitoring hook, NOT by importing server internals into the test process, since it's a separate OS process), time-to-connect per socket as concurrency ramps, `game:move` round-trip latency distribution (p50/p95/p99) as concurrent-room count increases, and behavior exactly at/past each of the three caps above (clean rejection vs. crash/hang).
- **This is inherently a resource-exhaustion test aimed at the local dev server** — per the "executing actions with care" guidance, don't run it against anything but a disposable local instance, and expect it may need the server restarted afterward (same as the guest rate-limiter needing a restart to clear, seen repeatedly this session).

## Legend

- **Priority** = risk (impact × likelihood), not effort. `Highest` > `High` > `Med` > `Low`.
  A `Highest`- or High-priority/Not-started row is the next thing to pick up,
  regardless of how many Passing rows exist elsewhere. `Highest` is reserved —
  currently only row 35.
- **Status** transitions: `Not started` → `Written` (spec exists, not yet run clean)
  → `Passing` (run green against the local server) or `Failing-bug-found` (real
  bug — must have a matching `TODO.md`/`instruction.md` entry, never silently fixed
  inline; see `CLAUDE.md` bug-fix workflow).
- Rows 6, 12, 14, 22, 23, 29-35 remain `Not started` as of the last pass — row 35
  (Highest) is the next one to pick up; the rest are picked in priority order for
  a follow-up session, not because they're less real.
